1. EXECUTIVE SUMMARY & CORE PRINCIPLES
================================================================================
Airborne Mesh is an offline-first disaster communication system engineered for
total connectivity disruption (floods, cyclones, earthquakes, infrastructure collapse).
It enables standard Android smartphones to communicate directly with zero cell
service and zero internet infrastructure, while allowing physical laptops or
airborne drones to harvest emergency data and return life-saving rescue directives.

Core Tenets Implemented:
1. ZERO INTERNET REQUIREMENT:
   Every core feature (emergency reporting, community road updates, peer discovery,
   database persistence, hop routing, and triage) operates 100% offline.
2. BRIDGEFY-STYLE BLUETOOTH LOW ENERGY (BLE) MESH:
   Phones communicate peer-to-peer using standard Bluetooth LE (BLE), operating
   simultaneously as BLE Advertisers (beacons) and BLE Scanners (radar) with GATT
   chunked message transport over Service UUID 0000FE60.
3. REAL-TIME AUTO-FORWARDING TO WEB COMMAND CENTER:
   The instant an Android phone receives an emergency distress report or location
   from another device over Bluetooth LE, it automatically forwards the payload
   to the laptop command base station (`POST /sync/transfer`) in real-time.
4. LIVE AUTO-REFRESHING WEB DASHBOARD:
   The laptop web server features a real-time command console that auto-polls
   live feed APIs, emits audio/visual chimes when new BLE distress signals arrive,
   and provides one-click interactive directive dispatching without page reloads.
5. PERSISTENCE-BEFORE-ACK:
   A node NEVER issues an acknowledgement payload until the message record has been
   physically committed to its local SQLite database.
6. BOUNDED EPIDEMIC STORE-AND-FORWARD:
   Messages hop between moving phones and base stations. Hop count is capped (10 hops),
   TTL expiration is strictly enforced, and records are deduplicated by UUIDv4.
7. DETERMINISTIC TRIAGE & EVIDENCE PRESERVATION:
   Contradictory reports (e.g. "Road blocked" vs "Road clear") are preserved as distinct
   historical evidence, flagged visually with disputed evidence banners, and scored
   by a deterministic priority triage agent citing exact message IDs.

2. SHARED DATA CONTRACT & PROTOCOL SPECIFICATION (`protocol/`)
================================================================================

File: protocol/message-schema.json
- Canonical v1 JSON schema contract defining all message payloads.
- Defines fields:
  * `schema_version`: Strict integer version (1).
  * `message_id`: UUIDv4 string identifier for idempotent deduplication.
  * `original_sender`: Pseudonymous node identifier of the originator.
  * `created_at`: Epoch timestamp (seconds) when report was generated.
  * `expires_at`: Epoch timestamp (seconds) for automatic TTL garbage collection.
  * `message_type`: Enum ["DISTRESS", "COMMUNITY_REPORT", "RESCUE_UPDATE"].
  * `status`: Enum ["CRITICAL", "URGENT", "NORMAL", "SAFE"].
  * `body`: Human-readable description (max 500 characters).
  * `emergency_details`: Type ("FLOOD", "FIRE", "MEDICAL", "TRAPPED", "COLLAPSE"),
    people count, and immediate hazards.
  * `location`: Latitude, longitude, accuracy in meters, and capture timestamp.
  * `hop_trail`: Array of HopEntry records (relay node ID, received timestamp).
  * `delivery`: DeliveryStatus tracking rescue state:
    ["CREATED", "SENT", "RECEIVED", "ACKNOWLEDGED", "RESOLVED"].

File: protocol/sync-protocol.md
- Protocol specification detailing the bounded store-and-forward state machine:
  1. Connection Phase: Bluetooth LE GATT connection on Service UUID 0000FE60.
  2. Handshake Frame: Version negotiation and capability exchange.
  3. Inventory Offer Frame: Lightweight list of unexpired (message_id, created_at, expires_at).
  4. Inventory Request Frame: Receiver returns list of missing IDs only.
  5. Batch Data Frame: Sender transmits missing message payloads in chunked MTU frames.
  6. Batch ACK Frame: Receiver returns list of successfully persisted message IDs.
  7. Reverse Sync: Peer roles reverse to achieve full bidirectional synchronization.
  8. Session Close: Clean GATT termination.

3. ANDROID NATIVE CLIENT IMPLEMENTATION (`android-app/`)
================================================================================

3.1. Architecture & Tech Stack:
- Target SDK: 35 | Compile SDK: 35 | Min SDK: 29 (Android 10+)
- Language: 100% Kotlin with Kotlin Coroutines and StateFlow architecture.

- Local Storage: Android Jetpack Room with SQLite database.

3.2. Bridgefy-Style Bluetooth Low Energy (BLE) Mesh (`BridgefyBleManager.kt`):
- Operates 100% offline without Wi-Fi, cell service, or internet.
- Service UUID: `0000FE60-0000-1000-8000-00805F9B34FB`
- Sync Characteristic UUID: `0000FE61-0000-1000-8000-00805F9B34FB`
- Node Info Characteristic UUID: `0000FE62-0000-1000-8000-00805F9B34FB`
- BLE Advertiser: Periodically broadcasts Service UUID and Node ID in service data.
- BLE GATT Server: Listens for incoming peer connections and reassembles chunked
  JSON payloads transmitted across multiple MTU frames (`C:<id>:<idx>:<total>:<data>`).
- BLE Scanner: Continuously scans for nearby peer advertisements with low-latency settings.
- GATT Client: Connects to discovered peers, negotiates 512-byte MTU, and writes missing
  batches sequentially.

3.3. Real-Time Auto-Forwarding to Command Web Server:
- `BridgefyBleManager` provides `onDistressReceivedViaBle` callback.
- In `MainActivity.kt`, whenever an emergency distress signal is received via Bluetooth LE:
  * Ingested into local Room/SQLite database.
  * If the laptop base station URL (`http://192.168.32.5:8000`) is configured and auto-forward
    is enabled, launches a coroutine calling `laptopSyncClient.forwardEmergencyDistress()`.
  * Instantly posts the emergency payload to `POST /sync/transfer` on the laptop server.
  * The web dashboard receives the signal, plays an audio alert chime, and displays the card!

3.4. Offline SQLite & Room Persistence Layer (`data/`):
- `AirborneMeshDatabase.kt`: Room database containing `MessageDao` with queries:
  * `getAllMessagesFlow()`: Real-time UI updates via Kotlin Flow.
  * `getMessageById(id)`: Single message retrieval.
  * `getAllMessageIds()`: Inventory set calculation.
  * `insertMessage(entity)`: ID-based deduplication with `OnConflictStrategy.IGNORE`.
  * `updateDeliveryState(id, state, ack, drone)`: Deterministic state transitions.
  * `purgeExpired(now)`: Automatic garbage collection of expired reports.
- `MessageEntity.kt`: SQLite Room entity mapping domain models to disk tables.
- `MessageRepository.kt`: Clean repository abstraction managing database operations,
  hop trail stamping, persistence-before-ACK verification, and reactive UI flows.

3.5. Deterministic AI Triage & Conflict Detection (`ai/DistressTriageAgent.kt`):
- Prioritizes emergency reports using deterministic rule-based algorithms:
  * Baseline priority: CRITICAL = 100, URGENT = 70, NORMAL = 40.
  * Hazard multipliers: Trapped victims (+30), Flood (+25), Collapse (+25), Fire (+20).
  * Casualty scaling: Up to +20 points proportional to number of affected people.
  * Time decay factor: Aging unacknowledged emergencies receive elevated priority.
- Conflicting Evidence Detection:
  * Scans community reports for contradictory assertions on the same location/resource
    (e.g., "Bridge collapsed" vs "Bridge clear and open").
  * Flags disputed pairs with `isConflicting = true` and identifies message IDs.
- Zero External API Dependency: Runs 100% locally on phone CPU in under 5 milliseconds.
